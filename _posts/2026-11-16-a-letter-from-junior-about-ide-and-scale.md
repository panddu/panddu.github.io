얼마 전 올렸던 [“진짜 IDE 안 써요?” 개발팀 스크린타임 결산](/essay/why-developers-dont-use-ide/) 영상과 글이 나간 뒤, 새벽에 취업을 준비 중인 한 대학생 구독자분께 메일 한 통을 받았습니다.

Java/Spring 백엔드 신입 취업을 준비하며 개인 프로젝트를 진행하고 계신 분이었는데, 영상 속 저희 팀의 일하는 모습을 보며 마음속에 복잡한 불안과 물음표가 생기셨던 모양입니다.

혼자 끙끙 앓다가 조심스럽게 보내주신 게 느껴져서 저 역시 그냥 지나칠 수가 없었는데요. 요즘 비슷한 혼란을 겪고 계실 취준생·주니어분들이 많을 것 같아, 질문자분의 개인정보는 가리고 제가 드렸던 답변과 생각을 함께 정리해 봅니다.

---

## 1. 새벽에 도착한 메일 한 통

질문자분은 현재 **헬스장·PT 예약 서비스**를 개인 프로젝트로 만들고 계셨습니다. 

코드 생성은 AI에게 맡기되, 그렇게 만들어진 코드를 IntelliJ IDEA에서 직접 열어 한 줄 한 줄 읽고 고쳐가며 개발하고 계신 상태였죠. 

그런데 저희 팀이 코드 작성부터 API 테스트, DB 접근까지 터미널(`herdr`, `cmux`) 안에서 처리하는 모습을 보고 크게 두 가지 고민이 드셨다고 합니다.

> **구독자분의 질문 요약**
>
> 1. **작업 방식에 대한 불안:** "AI가 만든 코드를 IDE에서 직접 읽으며 검증하는 지금 제 방식이 괜찮은 걸까요? 아니면 현업처럼 터미널 중심으로 일하는 방식에 미리 익숙해져야 할까요? IDE 없이 일하실 땐 코드를 어떻게 확인하시나요?"
>
> 2. **프로젝트 규모에 대한 불안:** "혼자 개발하며 엔티티 12개에 API 40개 정도를 설계했습니다. 프로젝트 규모가 너무 작은 건 아닌지 걱정됩니다. 어쩌면 규모가 작아서 IDE로 다 읽을 수 있는 건 아닐까 싶기도 하고요. 기능을 더 늘리는 게 좋을까요, 아니면 지금 기능을 더 깊게 파는 게 좋을까요?"

이 메일을 읽으면서 참 많은 생각이 들었습니다. 

최신 툴과 현업의 특이한(?) 워크플로우를 보여드리는 영상이, 어쩌면 성실하게 기본기를 다져가고 있는 분들에게 불필요한 조급함이나 자격지심을 드린 건 아닐까 하는 죄송한 마음도 들었고요.

---

## 2. "IDE냐 터미널이냐"는 아무 상관이 없습니다

첫 번째 질문인 **"IDE에서 직접 읽으며 검증하는 방식 vs 터미널 중심 워크플로우"**에 대해, 저는 **"지금 방식이 너무나 훌륭하고 정상적이다"**라고 말씀드리고 싶습니다.

솔직히 말씀드리면, 현업에 있는 저희도 올해는 완벽한 과도기입니다. 상반기 내내 온갖 삽질을 거치며 이제야 하반기쯤 되어 팀 나름의 패턴이 조금씩 잡혀가고 있는 중일 뿐이에요. 그러니 이제 막 발을 들이는 학생 입장에서 혼란스러운 건 너무나 당연한 일입니다.

저희 팀이 터미널로 일한다고 해서 IDE를 아예 안 보는 것도 아닙니다. 터미널에서 에이전트가 작업해 둔 결과물을 IDE 뷰어로 열어서 diff를 꼼꼼하게 검토할 때도 많고, 반대로 자잘한 버그 수정이나 스크립트 작업은 터미널 안에서 후딱 끝내기도 합니다. 상황에 따라 도구를 오갈 뿐이죠.

여기서 가장 중요한 건 **'내가 어떤 화면을 보고 있는가'가 아니라, 'AI에게 프롬프트 지침을 내릴 때 내가 이 일의 맥락을 얼마나 정확히 이해하고 있는가'**입니다.

내가 짠 시스템의 데이터 흐름과 비즈니스 로직을 머릿속에 꿰고 있는 사람이라면 터미널에서 작업하든, IntelliJ IDEA에서 작업하든, 심지어 메모장을 켜놓고 하든 아무런 문제가 되지 않습니다.

오히려 AI가 뱉어낸 코드를 IntelliJ IDEA에 띄워두고 **"이 코드가 왜 이렇게 짜였지?", "예외 처리는 제대로 됐나?"** 하고 직접 읽고 고쳐보는 지금의 훈련은, 주니어 시절에 절대 건너뛰어서는 안 되는 가장 소중하고 정석적인 과정입니다. 

그 '검증의 눈'이 없는 상태에서 남들 따라 터미널 멀티 세션만 띄워봤자, AI가 쳐놓은 환각(Hallucination)에 휘둘리며 모래성만 쌓게 될 뿐이니까요.

---

## 3. "엔티티 12개, API 40개"는 결코 작지 않습니다

두 번째 질문인 **프로젝트 규모에 대한 걱정**도 정말 많이들 하시는 단골 고민입니다.

제가 요즘 신입 채용 시장의 트렌드를 다 꿰고 있진 못하지만, 감히 말씀드리자면 **"엔티티 12개가 유기적으로 잘 얽혀 돌아가는 시스템이라면 결코 작은 규모가 아닙니다."**

면접관으로 들어가서 수많은 포트폴리오를 볼 때도 마찬가지입니다. 

단순히 화면 개수 채우려고 복붙해 넣은 API 100개짜리 쇼핑몰보다, 핵심 도메인 하나를 제대로 파고든 프로젝트가 열 배는 더 매력적입니다.

예를 들어 질문자분이 만들고 계신 **'헬스장·PT 예약 서비스'**만 해도 파고들 거리가 정말 무궁무진합니다.

* 인기 강사의 특정 시간대 PT 예약이 동시에 몰릴 때, **동시성 제어(Lock)**를 어떻게 처리해서 중복 예약을 막았는가?
* 사용자가 예약을 취소하거나 환불을 요청할 때, 회원권 차감과 스케줄 복구가 **단일 트랜잭션** 안에서 데이터 정합성을 유지하는가?
* 예약 시작 1시간 전 알림 푸시를 보낼 때, 수백 명의 대상을 어떤 스케줄러나 배치 구조로 부하 없이 처리할 것인가?

이런 고민들은 겉보기엔 API 한두 개, 엔티티 서너 개 사이에서 일어나는 일이지만, 이걸 제대로 고민하고 풀어내려면 DB 격리 수준, 트랜잭션 전파 속성, 락의 종류, 캐싱 전략까지 온갖 백엔드 기본기가 총동원되어야 합니다.

따라서 기능을 옆으로 넓혀서 API 개수를 80개, 100개로 늘리는 것보다, **지금 있는 40개의 API와 12개의 엔티티 사이에서 발생할 수 있는 '현실적인 장애와 엣지 케이스'를 아래로 깊게 파고드는 것**이 포트폴리오로서 훨씬 더 강력한 무기가 됩니다.

프로젝트가 작아서 IDE로 다 읽히는 게 아닙니다. 질문자분이 설계하신 구조를 질문자분이 잘 장악하고 계시기 때문에 읽히는 것이고, 그건 아주 건강한 신호입니다.

---

## 4. 마치며: 도구가 본질을 앞설 수는 없다

답장을 보내면서도 제가 너무 뜬구름 잡는 원론적인 이야기만 드린 건 아닐까 조금 조심스러웠습니다. 

하지만 아무리 세상이 바뀌고 현란한 AI 도구들이 쏟아져 나와도, 결국 일의 본질은 변하지 않는다고 믿습니다.

> **이해가 있는 사람은 도구가 있든 없든 일을 잘 해냅니다.**  
> **반대로 이해가 없는 사람은 아무리 좋은 도구를 쥐어줘도 금방 한계에 부딪힙니다.**

AI를 쓰느냐 마느냐, IDE를 켜느냐 터미널을 켜느냐는 그저 '취향과 작업 효율'의 문제일 뿐 실력의 척도가 아닙니다.

화려한 트렌드나 남들의 워크플로우에 시선을 빼앗겨 불안해할 필요가 전혀 없습니다. AI가 만들어준 코드를 내 눈으로 검토하고, 내가 설계한 12개의 엔티티가 서비스 안에서 왜 필요한지 치열하게 증명해 나가는 것. 

지금 걷고 계신 그 길 자체가 이미 아주 단단하고 올바른 방향입니다. 

자신감을 가지시고, 질문자분만의 멋진 예약 서비스를 끝까지 완성해 내시기를 진심으로 응원합니다. 화이팅입니다! 😄
